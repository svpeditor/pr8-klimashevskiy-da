# DECISIONS.md

## Вариант

Номер варианта: 4 (две последние цифры зачетки 25Т0859: 59 mod 8 + 1 = 4).

Изменяемый аспект: минимальная длина причины, параметр 25.
Правило, которое реализовано: причина отклонения обязательна и должна содержать
не меньше 25 символов (вместо 10). Пробелы в начале и в конце не считаются,
причина сохраняется уже без них.

Где сосредоточено: константа BusinessTrip.MIN_REASON_LENGTH = 25, ее использует
только метод reject, а SelfCheck берет границу из нее же.

## Таблица переходов состояний

- DRAFT -> SUBMITTED: submit(), только если заполнены сотрудник и место назначения
- SUBMITTED -> APPROVED: approve()
- SUBMITTED -> REJECTED: reject(reason), причина не короче 25 символов
- APPROVED -> COMPLETED: complete(today), только если today позже даты окончания
- DRAFT, SUBMITTED, APPROVED -> CANCELLED: cancel()
- все остальные переходы запрещены: IllegalStateException, статус не меняется

REJECTED, CANCELLED и COMPLETED - конечные состояния, из них переходов нет.
Картинка переходов: diagrams/states.png.

## Решение 1. Статус меняется только доменными методами

Формулировка: поля status нет в конструкторе и нет setStatus. Статус меняют только
submit, approve, reject, cancel и complete. Каждый метод сначала вызывает
checkStatus(действие, разрешенные статусы), и только потом проверяет данные и
меняет статус.

Альтернатива: публичный setStatus и проверка переходов в сервисе.

Обоснование: тогда объект сам защищает правила, и обойти их нельзя, даже если
забыть про сервис. Список разрешенных статусов виден прямо в каждом методе, его
легко сверить с таблицей переходов. При ошибке исключение бросается до изменения
полей, поэтому заявка остается в прежнем состоянии.

## Решение 2. Даты проверяются в конструкторе, обязательные данные - при отправке

Формулировка: конструктор не дает создать заявку без id, без дат или с концом раньше
начала. Сотрудник и место назначения заполняются методом fillDetails только в
черновике, а submit проверяет, что они есть.

Альтернатива: требовать все данные сразу в конструкторе.

Обоснование: правило из задания говорит, что SUBMITTED возможен только при
заполненных данных, значит черновик может быть неполным. А неправильные даты не
имеют смысла ни в одном статусе, поэтому их проще отсечь сразу.

## Результаты граничных проверок

- типовое значение: черновик -> submit -> approve -> complete на следующий день - COMPLETED
- нижняя граница дат: начало и конец в один день можно, конец раньше начала - ошибка
- граница причины: 24 символа - ошибка, 25 - REJECTED; пробелы по краям не считаются
- граница даты завершения: в день окончания нельзя, на следующий день можно
- пустое значение: пустой id, null дата, пустая причина - ошибка
- неверный формат: дата 2026-13-01 в файле - строка пропущена с сообщением
- повтор и конфликт: повторный submit, отмена после COMPLETED и после REJECTED,
  создание второй заявки с тем же id - ошибка, статус не меняется

Все проверки есть в SelfCheck (29 PASS), сценарии с ошибками есть в data/sample.csv.

## Собственные формулировки

### Какая проверка защищает от наиболее вероятной ошибки входных данных

Самая вероятная ошибка - перепутанные или неверные даты (конец раньше начала,
опечатка в месяце). Ее ловит конструктор BusinessTrip: дата окончания не может быть
раньше даты начала, даты обязательны. Опечатку в формате (2026-13-01) ловит разбор
строки в SelfCheck, такая строка пропускается с сообщением. Вторая частая ошибка -
слишком короткая причина отклонения, ее ловит reject.

### Какой метод или класс содержит ключевое бизнес-правило и почему

Ключевое правило - допустимые переходы между статусами. Оно в классе BusinessTrip:
в каждом доменном методе через checkStatus и в private методе checkStatus. Правило в
самом объекте, потому что только он знает свое текущее состояние и может не дать
перевести себя в запрещенное. BusinessTripService только создает заявки и ищет их
по статусу.

### Как Activity-диаграмма отражает участок кода

Блок A1 "Проверить, что текущий статус есть в списке разрешенных" - это вызов
checkStatus в начале каждого доменного метода, например checkStatus("отменить",
DRAFT, SUBMITTED, APPROVED) в cancel. Ромб "Переход допустим" - цикл внутри
checkStatus: если статус не нашелся, бросается IllegalStateException (блок "Зафиксировать
ошибку"). Блок A2 - проверки после него: в reject это длина причины.

### Какое изменение требования затронет минимум классов

Изменение минимальной длины причины (например, с 25 на 30) затрагивает один класс
BusinessTrip и одну константу MIN_REASON_LENGTH. Сервис и enum не меняются, а
SelfCheck берет границу из константы, поэтому общие проверки сами подстроятся,
поменять надо только явные проверки варианта на 24 и 25 символов. Так и сделан
мой вариант 10 -> 25.

## Фрагмент кода для анализа

public void setStatus(TripStatus status) { this.status = status; } позволяет поставить
любой статус в обход правил: например, перевести черновик сразу в COMPLETED или
отменить уже завершенную командировку, без проверки дат, данных и причины. Это ломает
все инварианты BusinessTrip. Исправление - убрать setStatus и менять статус только
доменными методами submit, approve, reject, cancel и complete, каждый из которых
проверяет допустимость перехода.
